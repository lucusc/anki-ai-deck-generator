## Exact proposed storage/deletion contract

One physical Azure Storage Table, such as `Metadata`, has logical
Documents/Cards/Decks/Jobs plus SourceHash/CardHash entities.
`PartitionKey = "u" + sha256(canonicalJSON(["anki-tables-v1", issuer, subject]))`.
Rows: `d:{deck}`, `j:{deck}:{job}`, `o:{deck}:{document}`,
`c:{deck}:{card}`, `s:{deck}:{sourceHash}:{compatibilityHash}`,
`h:{deck}:{cardHash}`. Deck guard replacement participates in each child mutation.
Server-generated removed mapping UUIDs are never reused.

Imported hash lookups are not an in-flight reservation, result cache, semantic
duplicate algorithm or quota ledger. #19 must decide compatible source-hash
inputs; #22 calculates card hashes. The schema supplies storage, not those
unassigned algorithms/APIs.

Proposed #18 private locator:
`{userPartition}/{deckUUID}/{jobUUID}/{artifactClass}/{artifactUUID}`.
References alone authorize nothing. Begin authenticated deletion by atomically
changing the deck guard to `deleting`, then drain outstanding Blob write
authority/delete raced and existing artifacts, then finalize Table cleanup.
The guard persists if cleanup fails. A check before PUT cannot stop an already
in-flight write or revoke previously issued SAS. **Parent/lead must accept a
concrete bounded drain/revocation/recovery protocol before #18 completion.**

Operational rows are denied at fixed creation + 30 days; `purge_expired()` removes
them for one user, including during deleting-state recovery. It does not discover
users or run automatically. **Physical 30-day retention needs a bounded monitored
inventory/sweeper with an earlier cleanup target and outage recovery.** No
server-clock transaction condition exists; lease/expiry checks are local and
ETags fence committed reclaim/deletion, not exact wall-clock arrival.
