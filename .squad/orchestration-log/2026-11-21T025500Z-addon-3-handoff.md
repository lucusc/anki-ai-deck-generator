## Acceptance coverage and stable destination proposal

Normal collection decks, including empty Default, are listed via
`all_names_and_ids(skip_empty_default=False, include_filtered=False)` in
collection-bound QueryOp. Filtered decks are visibly identified as ineligible
import targets. Selection is explicitly user-directed, does not change Anki's
current study deck, and makes no collection write.

Explicit Create new deck validates hierarchical names before collection access;
rejects empty components, whitespace/colon edges, controls and quotes; normalizes
NFC; checks existing names through supported case-insensitive lookup; and returns
`add_normal_deck_with_name()`'s change result through CollectionOp. Anki owns
undo/change notifications and any necessary parent-deck creation.

Immutable `DeckIdentity(deck_id, name)` plus a profile-local `DeckSelection`
retain the destination through dialog reopen. Refresh/reopening the Tools
window resolves the same ID, updates a renamed label with a notice, and displays
deleted/filtered targets without selecting Default or a name-reused replacement.
Profile close clears the holder. `revalidate_deck(collection, captured_target)`
is reusable by later review/import: capture the immutable target with its
collection lifetime and revalidate inside the same serialized operation as
the future write. Name is display metadata only. Actual review/import and
backend logical deck mapping are not implemented.

Single modeless Tools workflow preserves PKCE, protected refresh storage,
configuration failures, without_collection auth dispatch and profile
cancellation. Auth and deck controls gate each other. Queued deck work checks
close before collection access; late callbacks cannot update closed widgets.
Already-started creation can commit after close and is not silently deleted.
Errors/logging use fixed content-free codes; no deck names/IDs/content logged.

Contract proposal and limitations are fully recorded in
`addon-3-stable-deck-contract.md` and `docs/deck-selector.md`. Parent must
explicitly accept/consolidate the proposal. Parent can link the new document
from root documentation; the #1 foundation document describes its historical
sign-in-only milestone and was intentionally outside this write scope.
